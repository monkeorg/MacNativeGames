# Separate BOTW iPad assessment

Scope: [issue #8](https://github.com/monkeorg/MacNativeGames/issues/8), after the TOTK work in [roadmap #9](https://github.com/monkeorg/MacNativeGames/issues/9). This assessment is parked until the TOTK milestones are complete. It does not implement or enable a BOTW iPad build, widen version support, or transfer TOTK's device evidence to BOTW.

Source review: 2026-10-24, starting from `236930c`. Only repository source and existing documentation were inspected. No tests, probes, builds, simulators, game-input downloads, installation or gameplay were run, following the current user instruction. All future acceptance below remains unchecked.

## Version and platform inventory

BOTW shares the runtime and NVN-to-Metal layer under `games/totk`, as required by [CONTRIBUTING.md](../CONTRIBUTING.md). `games/botw` contains its input pins, shader list and preparation/research scripts; it is not a second complete runtime or an iOS application project.

| Other BOTW versions or releases | No corresponding entry in `build_app.py:VERSIONS` or version block in `game_version.h`. | Unsupported; do not infer compatibility from title/name similarity or a newer SDK. | No support claim. |

`build_app.py:TITLES`, `identify_game` and `identify_botw_update` identify content by title IDs and pinned ExeFS hashes rather than filenames. Existing pins also cover rewritten modules, RomFS and add-on images. Keep those checks and version separation; this assessment does not change verified tables.

The stronger existing Mac evidence makes 1.9.0 a reasonable candidate for the first later iPad feasibility slice, subject to a separate scope decision and privately available lawful inputs. Supporting it would not automatically support 1.6.0. The Mac record has known limitations, including sinking legs after save load, allocation growth, unverified cold-cache behavior, unverified real-controller motion/rumble, and no native-2K heap patch. These need their own triage and must not be described as fixed or iPad results.

The existing iOS target uses iOS 26 and device libraries built for iOS, not Homebrew Mac archives. Retain the Apple Silicon/native ARM64 execution model. `games/botw/scripts/botw190_unicorn.py` is a research script, not an allowed runtime backend or iPad acceptance route: the port must not introduce CPU emulation, interpretation or JIT.

## Reuse and separation plan

Keep one shared runtime, rewriter, HLE, NVN-to-Metal implementation and device library preparation path. Reuse module export/embedding, content verification, shader seed preparation, native input/lifecycle interfaces and diagnostics where their existing contracts apply. Reuse the launcher's deferred Play and save transaction mechanisms only after separating game-specific validation and capability decisions. Add parameters for demonstrated differences rather than copying the whole TOTK implementation.

Keep BOTW version pins and content preparation in `games/botw`, BOTW patch decisions in the existing game-specific sources, and generated products/caches in game-and-version-specific directories. A separate app target or generated project configuration should select those inputs explicitly. Do not define `GAME_BOTW` globally, mutate TOTK's version tables, repurpose its display profile, or overwrite its private build/save/cache artifacts. Any eventual change to shared code must demonstrate that the TOTK configurations retain their behavior and picture quality, alongside Mac BOTW coverage.

Use separate, focused implementation changes after the dependency gate: build selection and signed-code audit; data/AOC/shader packaging; app identity and startup; save-schema/launcher adaptation; then controls, lifecycle and graphics acceptance. Do not promise BOTW full-aspect 1080-high native 60 FPS from TOTK's roadmap target. BOTW render size, aspect behavior, heap capacity and performance need a separately agreed target and measurements.

## Ordered future acceptance

These are future gates, not instructions to execute tests now. Keep source implementation, build, installation, launch and gameplay evidence separate. No gate is checked by this document.

1. **Dependency and scope:** finish the agreed TOTK milestones; select one BOTW version and DLC matrix, device/OS and initial graphics target. Confirm private original inputs and a separate app identity. Record current Mac limitations and decide which block the feasibility slice.
2. **Build provenance and isolation:** complete guarded patch/export review, reproducible generated manifests and device packaging. In a later authorized validation session, check malformed/wrong-version input refusal and exact game/version source selection. Verify TOTK build artifacts and writable data stay isolated. Retain the public rejection until the device path is ready.
3. **Apple compilation and signing:** build selected BOTW device and Mac configurations plus affected TOTK configurations using the existing checks when authorized. Record exact revision, SDK, options, entitlements and artifact identity privately. Confirm all executable modifications precede signing and no runtime path needs writable signed text. A successful compile is not a launch result.
4. **Safe installation and startup:** back up the existing TOTK saves first, preserve its app and container, install BOTW separately on the physical target, then verify content attestation, title screen, fonts/audio, AOC enumeration where selected, and deferred game start. Record install and launch independently. Use no simulator resources for this workflow.
5. **Save safety and lifecycle:** establish BOTW-specific synthetic fixtures and schema checks before private save round trips. Later validate byte equality, identity preservation, failed-import rollback, backup/restore, no replacement after Play, relaunch and foreground/background behavior. Confirm a privately backed-up BOTW save loads and TOTK remains usable. Cross-version save compatibility requires evidence of its own.
6. **Gameplay correctness:** record the selected version and real scenes; inspect world geometry, animation/physics timing, menus/HUD, movies, camera/UI projection, texture filtering, input, controller/mouse release, motion/rumble where offered and AOC gameplay where selected. Revisit the Mac record's known issues. Do not hide platform faults by changing player/world state.
7. **Sustained measurement:** warm real scene routes and use Instruments, GPU capture and existing diagnostics first. Adapt the [baseline protocol](ipados-baseline.md) to BOTW with separately agreed numerical thresholds, synchronized memory/thermal evidence and at least a 30-minute session. Distinguish newly rendered game frames, present-call cadence and interpolated/displayed frames. Agree any picture tradeoff with before/after evidence; retain render/output resolution and Mac picture quality as required by CONTRIBUTING.
8. **Release decision:** publish sanitized evidence and remaining limits, then decide whether to enable only the verified version/configuration. A second version or DLC combination repeats its relevant gates. Neither source reuse nor a green build closes physical-device acceptance.
