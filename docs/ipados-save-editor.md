# Optional iPad save-value editor: contract and implementation gates

Issue: [#7 — optional version-validated save-value editor](https://github.com/monkeorg/MacNativeGames/issues/7).

Historical prerequisite review date: 2026-10-24. Source reviewed at `236930c`, including the save-transfer change `b10f4b8`. The initial logical target is the **rupee-wallet value only**; positions, world state, quests and inventory are excluded from the first slice. Production publication is **format/integrity-gated** because the repository does not establish a complete format/integrity contract for saves newly written by TOTK 1.4.3. Original copy-only candidate implementation now proceeds within the documented family boundary; it does not enable Apply.

The initial prerequisite review was manual. No tests, compilers, probes, simulators, game launches, private-save downloads, or device operations ran in that phase. Later source-only synthetic validation is separately recorded in the format-research follow-up. Earlier physical transfer results do not validate an editor.

Follow-up public research now identifies a pinned MIT-licensed **1.4.x family** signature and inline wallet field: see [the evidence and its limits](ipados-save-format-research.md). A separate read-only inspector and an original portable separate-buffer candidate serializer are implemented. The candidate serializer changes only the discovered wallet bytes and has synthetic native tests; it does not publish active saves. The full 1.4.3 format/integrity and physical-load gates below remain open.

The existing diagnostic editor means the repository is not entirely opaque about older saves. Its explicit version boundary must remain intact. Do not expand its admitted size/header set, reuse its hashes or vector assumptions for 1.4.3, or infer a new layout from the app version.

The reviewed save-related sources and tests provide no documented 1.4.3 field schema, integrity validation/update routine, or nonprivate format fixtures for an editor. No conclusion is made about undocumented private material or external tools.

## Inputs required before implementation

1. **Establish a 1.4.3 save-format contract.** Supply an independently documented, legally usable description of version discrimination, structure, rupee-wallet field lookup/encoding, lengths and bounds. Establish the field's type, legal range, dependent values and unsupported combinations from that verified contract. No offset, encoding, numeric range or integrity behavior is claimed here. The contract must explain how unsupported, truncated, duplicate or ambiguous records are refused. Identify its provenance and license before using third-party material; do not copy GPL implementation code into this MIT repository.
2. **Establish integrity requirements.** Document every affected checksum, digest, redundant value and cross-file relationship, with validation and update rules. If a rupee-wallet edit requires no integrity changes, provide evidence for that conclusion. A byte-difference report or a plausible value alone is insufficient.
3. **Provide nonprivate fixtures derived from that contract.** Use synthetic data with expected parsed values, expected permitted byte changes and documented integrity outcomes. Include unsupported versions, malformed structures, contract-defined boundary values and inconsistent dependent records. Do not commit real saves, account identifiers or game content. A synthetic transfer folder is not a save-format fixture.
4. **Arrange physical acceptance on the existing private setup.** Preserve the immediate original save and account identity. After the format and implementation are reviewed, retain the exact build/game version and private evidence that the supported rupee-wallet edit loads correctly and that restoration recovers the original. Do not enable the editor by default before a successful physical save load. Current device access and permission to run validation are separate prerequisites.

The first two inputs define what can safely be implemented; fixture work and field limits depend on that verified contract. The logical field selection is settled and is not an external blocker. Guessing offsets, adding unvalidated numeric controls, or implementing a write-only parser would leave the format and integrity prerequisites unresolved.

## Safety contract for a future implementation

The editor must remain optional and unavailable after Play. The Play handler's [`sealForPlay` call](../games/totk/ios/Sources/launcher.m#L224) seals the store before starting the game, and [`save_store.m:164`](../games/totk/ios/Sources/save_store.m#L164) checks that state for transfers. A future editing operation must use the same exclusion so editing cannot overlap Play or another save operation.

Keep a complete original backup before edits and change only a private stage. Validate the supported save version and all selected fields before writing, enforce field and transfer limits, update only documented dependencies/integrity data, and revalidate the completed stage. Publish through the existing validated replacement boundary or an equally reviewed extension; never patch the active save in place. [`save_store.m:189`](../games/totk/ios/Sources/save_store.m#L189) stages a complete incoming folder, validates it, backs up the current directory and uses same-volume atomic replacement. Parser validation is an additional requirement; current folder validation cannot substitute for it.

Preserve unrelated slot files, album/storage content and unknown bytes. Keep `account.uid` outside the replaced directory. Failures before publication must leave the active save unchanged, and the original backup must remain available for recovery. Permission, provider, parse, validation, integrity, storage and publication failures need explicit outcomes before the feature can be enabled.

## Save-transfer review boundary

The existing transfer path remains appropriate for opaque round trips. Imports coordinate provider reads and balance successful security-scope access in [`confirmImport`](../games/totk/ios/Sources/launcher.m#L315); copying or coordination failure does not reach the replacement step. The documented limits remain 64 MiB per file, 512 MiB total, 10,000 entries and 12 directory levels. The previous physical results in [the baseline](ipados-baseline.md#launcher-candidate-checks) belong to their recorded revision.

Manual review found no concrete compile-hook defect in `b10f4b8`: [`test_ios_save_store.py:23`](../tests/test_ios_save_store.py#L23) includes `dirent.h` before defining the wrapper macro and applies it only to `save_store.o`. [`ios_save_store_probe.m:18`](../tests/ios_save_store_probe.m#L18) defines that wrapper in a separate translation unit and calls real `readdir`, avoiding recursive redirection. The hook is not part of the production app build. Apple compilation and execution remain unverified in this review.

The directory metadata check in [`save_store.m:99`](../games/totk/ios/Sources/save_store.m#L99) rejects detectable membership changes during that directory's traversal. It does not freeze already-read files or provide a transaction across an external provider. Keep the existing instruction not to modify saves during transfers or gameplay; do not represent this check as a save-format integrity validator.

Production Apply remains blocked on the 1.4.3 format/integrity evidence and contract-derived fixtures above; enabling it also requires physical load and recovery evidence. Issue #7 is active for the bounded native candidate and transaction work described below. Issue #3's latest Apple build, provider failures and physical transfer/load acceptance remain separate from this prerequisite review.

## Bounded native editor integration plan

The first field is rupees only, using the pinned MIT reference's family tuple, inline scalar tag and reference UI policy. `mng_totk_save.h/.c` supplies original candidate parsing and serialization; no checksum is guessed. Production Apply remains unavailable until the exact-version/integrity gates above are satisfied. An exported candidate must be labelled unverified raw candidate bytes, never automatically imported or presented as a normal validated Canopy save export.

The Canopy transaction extension keeps an opaque private preview snapshot under `CanopySaveStore` authority, bound to the title/profile instance, selected file and complete original manifest digest. The immutable preview supplies the selected bytes to the native candidate editor. Its constructor-authorized Apply rechecks session seal/recovery state and the active manifest digest, refuses stale or foreign previews, edits only the private stage, validates the before/after file contract and completed stage, then uses the existing backup and `publishStage` journal/atomic exchange. This transaction mechanism is implemented; production TOTK has no qualifying edit validator and therefore cannot Apply. Accounts and identity stay outside the replacement, and all unrelated files remain byte-identical. Both a constructor-only trusted file edit validator and the existing full-stage validator are required; existing constructors leave editing unavailable. `previewEditForSlot:` copies the complete active tree, `applyEditPreview:replacementData:error:` applies only an authorized selected-file change, and `discardEditPreview:error:` retires its own opaque preview. Sealing invalidates prior previews even if the session token is subsequently released. Synthetic fixture authorization does not qualify the real TOTK format.

After the core is reviewed, the native UI caller should select a slot, show the family/integrity limitation and old/new rupee preview, then allow an explicitly labelled candidate share. It should provide no active Apply action while publication is gated. Parsing/copying runs on the existing serialized save worker; the UI stays busy until authoritative completion, handles cancellation/background transitions, and never logs wallet values or save bytes. Preview tokens cannot cross profiles or survive a store instance.

Original TOTK app reuse is a follow-up: adapt its existing slot/editor entry to the same candidate core and limitation labels, and retain its reviewed pre-Play save authority. Do not replace its active save directly or change its existing web-editor admission as an incidental part of the Canopy implementation. Apple compilation, physical editing/load and restoration are separate gates for each app.

The extended native save probe has ten additional editor test methods (32 methods total). It uses a test-only invented one-byte `A`→`B` format, not a TOTK validator, to exercise the real snapshot/CAS, mandatory backup, publication and journal paths. Cases include default-disabled Apply, unrelated active-tree changes, foreign profiles, snapshot tampering, seal invalidation, rejected fields, a mutating full-stage validator, persistence/backup refusal, outside symlinks, actual process exits after swap and durable commit, and ambiguous post-swap I/O recovery. All 32 are explicit Linux skips pending macOS Foundation execution; no Apple build or real-save acceptance is claimed here.

## Original TOTK native candidate sheet (source implementation)

The original iPad launcher now has a separate **Unverified rupee candidate** entry before Play. It does not replace **Edit this save**, which still opens the existing online editor. The new `save_candidate.h/.m` sheet uses the same original `launcher/src/mng_totk_save.c` candidate parser/serializer as Canopy; `ios/project.yml` includes that source directly rather than copying it.

The launcher holds its pre-Play busy guard for the whole candidate flow. A dedicated serial queue calls the actual `TOTKSaveStore.exportToDirectory` to create a private bounded snapshot, reads only supported-slot `progress.sav` copies with no-follow descriptor checks, and presents only those readable snapshots. Before a share, the same queue exports again through the store and compares the selected bytes with the visible preview. A changed or unavailable snapshot requires closing and reopening the sheet. The store's existing seal remains the authority for snapshot access. There is no save-directory migration or account-identity change.

The native sheet accepts whole-number input under the pinned reference editor's UI policy, displays the family/integrity limitations, and shares only explicitly confirmed raw `public.data` with an unverified-candidate suggested filename. Its completion returns no edited bytes: it cannot feed the online editor's `applyEditedProgress` callback, and it never calls import, replacement or Apply. Backgrounding invalidates pending selection or sharing; pending queue work finishes before cleanup releases the launcher's busy guard. The private workspace is cleaned independently of active saves.

This is source implementation only. No new tests, probes, compiler checks, simulators, private inputs, app launches, installations or device operations ran for this Track A follow-up. Format/integrity evidence, Apple compilation and real-save compatibility remain separate gates. Production native-candidate Apply remains unavailable.
