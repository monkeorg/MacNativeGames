## Evidence rules

Use `passed`, `failed`, `not run`, or `blocked` for each check. A blocked check has
no functional result. Record command, revision, environment, result and evidence
location. Separate source review, portable test, Apple compilation, signing,
installation, launch and gameplay. Old Track A results retain their original
revision/date and do not validate this launcher.

For device evidence record Xcode/SDK, device model and OS, signing/distribution
mode, debugger attachment, relevant entitlements, artifact hash and exact
title/version. Keep provisioning identities and device identifiers private.
Record native rendered frames separately from interpolated and presented frames;
a HUD counter or successful draw does not establish correct or sustained gameplay.

## Proposed private storage contract

This is an **unimplemented contract**, pending the native preparation/execution
backend and filesystem review. It does not authorize migration of Track A. Paths
below are relative to a new host's private Application Support root; identifiers
are validated internal keys, never unchecked provider filenames. Imported assets
stay outside the public app bundle.

```text
titles/<title-key>/
  sources/<source-key>/                 retained user-supplied source, if requested
  manifests/<manifest-key>.json         private identity/integrity/provenance
  versions/<version-key>/
    staging/<transaction-key>/          unpublished, bounded preparation work
    generations/<generation-key>/      immutable completed preparation
    current                            atomically published generation reference
  caches/<cache-key>/                   regenerable prepared resources
profiles/<profile-key>/
  account/                             identity; never replaced by save import
  saves/<title-key>/                    active title saves
  backups/<title-key>/                  verified save backups
```

The manifest binds exact base/update/DLC identity and dependencies, input hashes,
preparation recipe/tool fingerprints, output hashes and schema version. A cache
key includes content and recipe identity plus device/OS/graphics compatibility
where its format requires them. A cache hit is reusable data, not an executable
permission or game compatibility assertion. Settings use the same explicit title
and profile identities. Sources/manifests, caches and saves have separate retention
policies; generation garbage collection cannot traverse into account, saves or
backups, nor remove a current/in-use generation. Retained sources require an
explicit storage policy and must not silently duplicate every selected folder.

Before committing to a publication implementation, verify atomic-reference and
durability semantics on the real device filesystem. The intended acceptance is:

1. Prepare generation B while current generation A remains usable. Reject wrong
   title/version, inconsistent update/DLC, invalid outputs and insufficient space
   before publishing B; account and saves remain unchanged.
2. Cancel or kill preparation during copy, validation and final publication in
   separate runs. Relaunch; observe one valid current generation, useful recovery
   status, bounded cleanup and unchanged saves/identity. Never expose a partial B.
3. Inject low-space/read/write/provider failures before and during preparation.
   Reuse A, report the failure, and reclaim only abandoned staging proven unused.
4. Publish verified B, launch and relaunch it, then exercise rollback to retained A
   if B fails validation or activation. Record that each reference resolves to a
   complete matching manifest/generation; do not change save formats implicitly.
5. Update the host app and independently change recipe/game/device compatibility.
   Verify deterministic cache reuse or invalidation, measured transfers/storage,
   and retention of current/in-use generations. Test garbage collection with
   synthetic sentinels in account, saves and backups before any private data run.

1. **Prepare without disturbing Track A.** Use a separate checkout/build target and
   distinct harness app identity. Preserve the working TOTK app, private inputs,
   caches and signed rollback artifact. Before any authorized install touching
   user data, take an immediate private full-profile/account snapshot and hashes.
   Do not migrate or overwrite the existing app as an experiment.
2. **Run full source checks on the Mac.** Use the repository's pinned Python
   environment, then `python -m unittest discover -s tests`, plus the focused
   launcher tests above with that interpreter. Run the relevant native probes and
   existing iPhoneOS platform-probe build from its README. The production-loader
   integration harness remains pending. Record missing prerequisites
   and exact build/sign/install/run commands supplied by the harness implementation.
   No simulator setup is required by this handoff.
3. **Execute the signed original-source fixture.** Inspect the produced app's
   inventory and signatures before installation. Verify computed results, memory
   effects, host-call behavior, mapped permissions and expected refusal controls
   on the physical iPad. Repeat without the debugger. Identify the provisioning
   mode; a debug build does not establish the behavior of a released IPA.
4. **Resolve the external-module question.** Under the intended distribution and
   signing model, can a content-free public host access and execute a separately
   prepared private ARM64 module that was absent from its signed executable?
   Name the supported mechanism, who signs which artifact and when, required
   entitlements, sandbox access path, signature acceptance and executable mapping
   behavior. Demonstrate with original-source bytes first, without a debugger,
   JIT, interpreter or emulator. Repeat after relaunch and a supported app update.
   Record the exact system error if refused. A Mac-signed private game app or
   embedded fixture answers a different question and leaves this gate open.
5. **Validate one declared title/version.** Only after step 4 succeeds, use retained
   private user inputs locally. Verify base/update/DLC identity before preparation,
   initial shaders/resources, completion/cancellation/provider loss/storage errors,
   real gameplay and cold relaunch. A successful parser or decrypted file is not
   title support. Review final public artifact provenance separately from private
   preparation content.
6. **Verify settings, saves and updates.** Exercise each game's independent settings
   and capability restrictions, live versus next-launch effects, focus/background
   transitions, accessibility and controllers. Export/import/restore the user's
   own save before Play, compare bytes and account identity privately, and load it
   in-game. Reject wrong-title/version input and require unchanged active data on
   cancellation/failure. Keep semantic editors disabled until the exact format is
   independently validated. During Play, refuse replacement/backup/restore through
   the sealed store. Test app upgrade and recipe/game/update/DLC changes separately;
   verify cache reuse/invalidation, bytes transferred and storage. Interrupt
   publication at controlled boundaries and require the previous usable generation,
   saves and identity to remain intact. Compare against the immediate pre-action
   snapshots, not an older baseline.
7. **Verify Mario Kart separately.** Declare the exact Switch title/version and
   supported local mode/player count. Prove its native profile and required host
   services, then complete an actual local race/session with at least two players
   using independent controllers. Confirm that one controller cannot drive another
   player, including simultaneous opposing inputs. Test disconnect/reconnect,
   explicit reassignment and overlay/focus transitions without stuck inputs. A
   player-assignment UI, controller enumeration or TOTK session does not pass.
8. **Close only evidenced gates.** Record graphics correctness, agreed sustained
   performance thresholds, synchronized memory/thermal/storage and lifecycle
   results. Link each architecture requirement to its tested revision. Failed or
   unavailable checks stay open. This checklist does not authorize a merge/release.

## Privacy and evidence publication

Keep raw game-derived binaries/resources, source containers, keys, saves, account
identifiers, device identifiers, signing identities/profiles and private paths out
of Git, issues and cloud uploads. A log can contain payload bytes or identifiers
even when its filename looks harmless. Review/redact logs before publishing;
retain raw evidence privately and publish only enough sanitized facts to assess
the result. Public original-source fixture artifacts are distinct from private
game artifacts. Do not treat an ignore rule as proof that a file is safe to share.

## Work while native execution is unresolved

is bounded by an observable contract: strengthen production-path rewrite and
section negative controls; implement the pending production-loader integration harness; add parser
short-read/overflow/resource-bound tests and sanitizers; document and test artifact

and specify private generation publication/recovery with synthetic fault injection

release completion. Implement deeper parsing/decryption only for declared formats
with known requirements and appropriate local evidence.

Do not fill the blocked interval with a pretend game library, unsupported profile
catalog, unconnected settings/player UI, duplicate engine or speculative updater.

single-player runtime requires separate integration and regression evidence.
When useful bounded checks and the harness source are complete, the remaining
critical task is local Apple signing/external-module execution evidence. If that
path fails or remains unavailable, record the precise blocker and preserve a
reviewable checkpoint; do not weaken the product gate or claim completion.
